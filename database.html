01

Why the Database Exists

The Developer Sandbox contains different kinds of material that share common information but require different page structures. Projects, reference guides, experiments, Rosetta Stones, technical documentation, and other resources all need titles, descriptions, classifications, statuses, technologies, and content.

Storing that information as structured data prevents each item from becoming an isolated collection of hard-coded fields. A common datastore makes content searchable, classifiable, reusable, and manageable from a single editor.

02

Why SQLite

SQLite provides a relational database without requiring a separate database server. The complete datastore can remain inside the Sandbox project while still providing tables, relationships, foreign keys, transactions, indexes, and SQL queries.

This makes it appropriate for a local authoring system: the data is persistent and relational, but the project does not need a continuously running PostgreSQL, MySQL, or other external database service simply to maintain Sandbox content.

The working database is stored as data/sandbox.db. Database definitions and migrations are kept separately under the database/ directory so the structure of the datastore is visible in source control.

03

Relational Structure

Records form the central catalog of Sandbox content. Related tables connect those records to categories, tags, technologies, and page content without duplicating the same classification data inside every record.

04

Records — The Entry Layer

The records table stores the identity of each major Sandbox item. A record can represent a project, reference document, Rosetta Stone, experiment, visualization, resource, or another content type.

Record fields include the ID, title, slug, subtitle, description, type, status, visibility, featured state, sort order, creation and update timestamps, presentation mode, navigation information, parent information, notes, and optional custom classes.

The Entry remains separate from its detailed page content. This allows catalog information to be searched and displayed without requiring the system to parse an entire page structure.

05

Content Nodes — The Page Layer

Detailed page content is stored in content_nodes. Each node belongs to a record and can contain a type, title, subtitle, description, navigation label, content, sort order, visibility state, custom class information, and additional metadata.

A node with no parent_id is a top-level Parent Node. A node whose parent_id references another node is a Child Node. This creates a controlled hierarchy for constructing page sections.

06

Node Metadata

The core fields required by nearly every Content Node remain normal relational columns. Less universal presentation settings can be stored in the node's metadata field as structured JSON.

This prevents the schema from accumulating a new column for every optional visual or behavioral setting while preserving a stable relational structure for the fields that need to be queried directly.

07

Categories

Categories provide broader structural classification. The record_categories junction table allows a single record to belong to multiple categories and allows one category to be associated with many records.

Categories can also reference a parent category, allowing the taxonomy itself to develop a hierarchy without embedding category names directly into each Sandbox record.

08

Tags

Tags provide more flexible descriptive classification. Records and tags are connected through record_tags, creating another many-to-many relationship.

Because tags are stored as independent records rather than repeated text fields, the same tag can be reused consistently across projects and queried as part of the Sandbox search system.

09

Technologies

Technologies are modeled separately from ordinary tags because they carry technical meaning of their own. A technology can include its name, type, slug, description, official URL, and category relationship.

The record_technologies junction table connects technologies to records and can also describe a technology's role and display order for that particular project.

10

Connection to the Local Editor

The browser-based editor interface does not manipulate the SQLite file directly. Its TypeScript client sends requests to the local Node.js server, which owns the database connection and performs the required SQL operations.

This creates a clear boundary between interface code and database operations. The client is responsible for the editing experience while the server controls file access, SQL execution, database reads, and database writes.

11

Database Operations

The local server provides CRUD operations for Entries and Content Nodes along with specialized operations required by the Sandbox hierarchy. Nodes can be reordered or moved between parents, and moving a former Parent Node beneath another Parent is handled so the hierarchy remains limited to the intended two levels.

Bulk deletion is available for records and nodes. When records are removed, associated relationship rows and content nodes are removed as part of the operation so orphaned data is not left behind.

12

Foreign Keys and Data Integrity

SQLite foreign-key enforcement is enabled when the editor server opens the database. Relationship tables reference their parent records, and several relationships use cascading deletion where removing a parent should also remove dependent data.

Transactions protect operations that require multiple SQL statements. A group of related changes can be committed together, while an error causes the transaction to roll back rather than leaving the database only partially updated.

13

Content Ordering

Content Nodes include a numeric sort order. Parent Nodes and children are ordered among their own siblings, allowing the editor to rearrange page content without changing IDs or rebuilding the underlying records.

Reordering operations normalize sibling values and then exchange positions. This keeps the visible page order explicit in the database instead of relying on insertion order.

14

SQL Validation and Batch Operations

The local editor also includes direct SQL tooling for situations where structured batches are more efficient than entering large amounts of content manually.

Validation runs SQL inside a SQLite savepoint and then rolls the operation back. This allows syntax and database compatibility to be checked without saving changes. A separate Run operation wraps the submitted SQL in a transaction and commits only after the complete batch succeeds.

15

Search

The editor search queries the record ID, title, slug, type, status, description, categories, and tags. Because categories and tags live in relational tables, those relationships can be searched without duplicating their values into the primary records table.

16

Connection to the Sandbox Website

The database exists to provide a structured content source for the Sandbox system while keeping authoring separate from public presentation. Entries describe what exists in the Sandbox and Content Nodes describe how the detailed content can be assembled into page structures.

The local editor provides the write environment and preview workflow. The public-facing Sandbox can remain lightweight and does not need to expose the database editing routes in order for the source architecture to remain inspectable in the repository.

17

Schema and Migration Files

The initial relational structure is documented in database/schema.sql. Later editor requirements are recorded separately in database/editor-migration.sql rather than hiding structural changes inside application code.

This keeps the evolution of the datastore visible and provides a reproducible description of the tables, relationships, indexes, and fields used by the editor.
