FAST PATH

Mac-first testing stack

Use the fastest layer that can answer the question, then move to a more realistic environment only when needed.

Recommended default: manual browser checks + Playwright automation + Safari/Xcode verification + at least one real-device pass before important releases.

1 · Inspect quickly

Use Chrome, Firefox, and Safari responsive tools while building. Check layout, overflow, focus states, touch-sized controls, network requests, and console errors.

2 · Automate engines

Use Playwright Test as the modern default for repeatable Chromium, Firefox, and WebKit coverage. Add mobile device profiles as projects.

3 · Verify Apple

On macOS, use Safari Responsive Design Mode and Xcode Simulator for iPhone/iPad Safari behavior that desktop emulation cannot fully prove.

4 · Check physical devices

Use BrowserSync on the local network to load the same development site on phones, tablets, and extra browsers at the same time.

5 · Release on real hardware

Before a major release, test at least one physical iPhone/iPad and Android device, or use a real-device cloud such as BrowserStack.

WHICH TOOL?

Tool picker

These are complementary tools. The strongest workflow uses several layers instead of expecting one tool to prove everything.

Playwright

Best modern default. Open source. E2E/browser automation across Chromium, Firefox, and WebKit; strong device emulation, traces, parallelism, and CI support.

Cypress

Best for interactive JS/TS test authoring. Open-source runner with excellent local debugging and component testing. WebKit remains experimental, so do not treat it as complete Safari proof.

Selenium

Best for broad enterprise or cross-language needs. Open source, W3C WebDriver based, large ecosystem, Selenium Grid, and modern automatic driver management.

Safari + Xcode

Best Apple-platform check on a Mac. Built into macOS plus free Xcode simulators. Use Web Inspector, Responsive Design Mode, and iOS/iPadOS Simulator.

BrowserSync

Best low-friction local device lab. Open source. Serves or proxies a local site, reloads connected browsers, and can mirror scrolling, clicks, and forms.

Lighthouse

Best quick quality audit. Open source. Performance, accessibility, best-practice, and SEO audits from Chrome DevTools or the CLI.

axe-core

Best automated accessibility layer. Open source. Add checks to Playwright, Selenium/WebDriver, React, or other test workflows; manual accessibility review is still required.

BrowserStack

Best optional real-device cloud. Commercial, not open source. Useful for real iOS/Android hardware, many browser/OS combinations, and testing localhost through a secure tunnel.

BUILD-TIME CHECKS

Manual browser & device checks

Three columns show Use it for → macOS setup/open → best practice.

Do not confuse responsive emulation with real-device testing. Emulation is fast and valuable, but it cannot reproduce every CPU, GPU, keyboard, browser chrome, OS integration, memory, and touch behavior.

Chrome Device Mode

Use it for
Viewport resizing, DPR presets, CPU/network throttling, geolocation, orientation, layout inspection.

Open on Mac
⌥⌘I for DevTools, then toggle the device toolbar. Chrome Device Mode is an approximation, not a real phone.

Best use
Fast first-pass responsive debugging. Follow failures or suspicious behavior with a physical device or simulator.

Firefox Responsive Design Mode

Use it for
Responsive layout in Gecko, viewport size, touch simulation, DPR/device presets, and Firefox-specific CSS behavior.

Open on Mac
⌘⌥M or Firefox → Tools/Browser Tools → Responsive Design Mode.

Best use
Run after Chromium checks so Gecko-specific layout and standards differences are not missed.

Safari Responsive Design Mode

Use it for
WebKit/Safari layout, media queries, pixel ratio, Web Inspector, Apple-platform browser behavior.

Enable on Mac
Safari → Settings → Advanced → Show features for web developers. Enter Responsive Design Mode with ⌃⌘R; Web Inspector with ⌥⌘I.

Best use
Required macOS check for Safari. Use Xcode Simulator or a physical iPhone/iPad when mobile Safari behavior matters.

Xcode Simulator

Use it for
iPhone/iPad Safari in simulated iOS/iPadOS environments, different device sizes, OS versions, and Apple-specific behavior.

Install
Install Xcode from the Mac App Store, launch it once, then add runtimes in Xcode → Settings → Components. Safari can open pages in installed simulators from the Develop menu.

Best use
Closer to iOS than desktop viewport emulation, but still not physical hardware. Keep one real-device pass for release confidence.

REPEATABLE REGRESSION

Automation frameworks

Use automation for behaviors you need to verify repeatedly: navigation, forms, authentication, responsive menus, critical flows, and regressions.

Do not automate every visual detail. Automate stable user outcomes and critical UI states; keep exploratory and visual judgment in manual testing.

Playwright — recommended default

Modern cross-engine E2E testing with a strong TypeScript/JavaScript workflow, automatic waiting, traces, screenshots, network control, projects, and device profiles.

Install: run npm init playwright@latest in a project. The initializer can add TypeScript, tests, browsers, and a GitHub Actions workflow.

  • Use when: you want one test API for Chromium, Firefox, WebKit, desktop, and emulated mobile.
  • Best implementation: define browser/device projects in playwright.config.ts; keep locators user-facing; use web-first assertions; run a small smoke matrix on every change and the full matrix in CI.
  • Important: Playwright WebKit/mobile profiles are excellent engine/emulation coverage, but they are not a substitute for every branded Safari + real iPhone/iPad behavior.
Cypress — interactive JS/TS option

Open-source testing tool with an excellent interactive app, time-travel-style command debugging, network stubbing, E2E testing, and component testing.

Install: npm install cypress --save-dev, then npx cypress open.

  • Use when: the team is strongly JavaScript/TypeScript and values a highly visual local authoring/debugging loop or component testing.
  • Best implementation: use Chrome for Testing for deterministic Chromium runs; add Firefox; treat WebKit as experimental unless your release process also includes Safari/real-device validation.
  • Tradeoff: excellent developer workflow, but less straightforward as a single all-engine mobile-web answer than Playwright.
Selenium — enterprise & cross-language

Long-lived open-source browser automation built around W3C WebDriver, with language bindings, Selenium Grid, and broad browser/ecosystem support.

Install for JavaScript: npm install selenium-webdriver. Current Selenium uses Selenium Manager automatically, so ordinary setups no longer need manual ChromeDriver/GeckoDriver downloads.

  • Use when: you need Java/Python/C#/Ruby/JS teams, existing Selenium infrastructure, remote grids, or broad/legacy browser coverage.
  • Best implementation: use current Selenium 4+, explicit user-focused waits/assertions, and WebDriver BiDi capabilities where needed; avoid old tutorials that instruct you to hand-maintain browser drivers.
  • Tradeoff: broader ecosystem and language reach, but usually more framework/infrastructure work than Playwright for a new JS/TS web project.
BrowserSync — synchronized manual testing

BrowserSync is not an E2E assertion framework. It is an open-source local server/proxy and synchronization tool for testing the same page across several real browsers/devices at once.

Install locally: npm install browser-sync --save-dev. Local installation is preferred for project reproducibility.

  • Use when: you have phones/tablets on the same network and want one development URL, live reload, CSS injection, and optional scroll/click/form mirroring.
  • Best implementation: use server mode for static sites and proxy mode when a PHP/Node/etc. server already exists. Open BrowserSync's External URL on each physical device.
  • Tradeoff: excellent for visual/manual cross-device sweeps; it does not replace automated assertions or a real-device cloud.
TERMINAL + CONFIG

Copy/paste setup & examples

These examples are macOS-friendly and assume a current Node.js project. Install project tooling locally unless there is a strong reason to install it globally.

Playwright — initialize and run

Scaffold Playwright Test, install browser binaries, run all projects, open UI mode, and show the report.

Example 
npm init playwright@latest

# If browsers were not installed during setup:
npx playwright install

# Run the suite
npx playwright test

# Interactive test UI
npx playwright test --ui

# Open the last HTML report
npx playwright show-report
Playwright — cross-engine + mobile projects

Run the same tests against the three major browser engines plus representative mobile profiles. Device names below are from Playwright's documented device registry.

Example 
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  use: {
    baseURL: 'http://127.0.0.1:4173',
    trace: 'on-first-retry'
  },

  projects: [
    {
      name: 'Chromium',
      use: { ...devices['Desktop Chrome'] }
    },
    {
      name: 'Firefox',
      use: { ...devices['Desktop Firefox'] }
    },
    {
      name: 'WebKit',
      use: { ...devices['Desktop Safari'] }
    },
    {
      name: 'Mobile Chrome',
      use: { ...devices['Pixel 5'] }
    },
    {
      name: 'Mobile Safari',
      use: { ...devices['iPhone 12'] }
    }
  ]
});
Playwright — responsive navigation test

Example of testing a user-visible responsive behavior instead of only checking a viewport size.

Example 
import { test, expect } from '@playwright/test';

test('mobile navigation opens', async ({ page }) => {
  await page.goto('/');

  const menuButton = page.getByRole('button', { name: /menu/i });
  await expect(menuButton).toBeVisible();

  await menuButton.click();

  await expect(
    page.getByRole('navigation')
  ).toBeVisible();
});
Cypress — install, open, run browsers

Install locally, use the Cypress App while authoring, then run repeatable headless checks in chosen browsers.

Example 
npm install cypress --save-dev

# Open the interactive Cypress App
npx cypress open

# Headless run in Chrome
npx cypress run --browser chrome

# Headless run in Firefox
npx cypress run --browser firefox
Cypress — simple responsive test

Use viewport changes to exercise responsive behavior, then assert the outcome users actually need.

Example 
describe('responsive navigation', () => {
  it('opens the mobile menu', () => {
    cy.viewport(390, 844);
    cy.visit('/');

    cy.findByRole('button', { name: /menu/i }).click();
    cy.findByRole('navigation').should('be.visible');
  });
});
Selenium — JavaScript quick start

Selenium Manager handles the ordinary browser-driver setup automatically in current Selenium.

Example 
npm install selenium-webdriver

# example.mjs
import { Builder, Browser } from 'selenium-webdriver';

const driver = await new Builder()
  .forBrowser(Browser.CHROME)
  .build();

try {
  await driver.get('http://127.0.0.1:4173');
  console.log(await driver.getTitle());
} finally {
  await driver.quit();
}
BrowserSync — static and dynamic sites

Use the External URL printed by BrowserSync on other devices connected to the same local network.

Example 
npm install browser-sync --save-dev

# Static HTML/CSS/JS site
npx browser-sync start --server --files "css/*.css, js/*.js, *.html"

# Existing local server (example)
npx browser-sync start --proxy "http://localhost:3000" --files "css/*.css, js/*.js, *.html"

# Show CLI help
npx browser-sync start --help
Lighthouse — CLI audit

Chrome DevTools already includes Lighthouse. The CLI is useful for repeatable local or scripted audits.

Example 
npm install -g lighthouse

# Audit a running page
lighthouse http://127.0.0.1:4173

# See all CLI options
lighthouse --help
axe-core with Playwright

Add automated accessibility checks to a browser test. Automated checks catch only part of accessibility; continue keyboard, focus, zoom, contrast, and screen-reader review manually.

Example 
npm install -D @axe-core/playwright

import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('page has no automatically detectable a11y violations', async ({ page }) => {
  await page.goto('/');

  const results = await new AxeBuilder({ page }).analyze();

  expect(results.violations).toEqual([]);
});
PERFORMANCE + ACCESSIBILITY

Quality checks beyond layout

Cross-device quality includes more than width. Test performance, input methods, accessibility preferences, network behavior, and failure states.

Lighthouse

Catches quickly
Performance opportunities, accessibility signals, best-practice issues, and SEO basics.

Best implementation
Use Chrome DevTools while developing; use the CLI or CI tooling when you need repeatable audits. Treat scores as signals, not as a substitute for real-user performance data.

axe-core

Catches quickly
Many automatically detectable accessibility violations in rendered UI.

Best implementation
Run axe after important UI states become visible. Pair it with keyboard-only navigation, visible focus checks, zoom/reflow checks, labels, reading order, and manual assistive-technology review.

Network + CPU

Catches quickly
Slow-loading assets, blocking requests, loading-state bugs, timeouts, and code that assumes desktop CPU/network speed.

Best implementation
Throttle network/CPU in Chrome DevTools and test slow-state UI. Real mobile hardware remains the stronger performance check because desktop throttling cannot reproduce every mobile processor/GPU condition.

Touch + user preferences

Catches quickly
Controls too small for touch, hover-only interactions, motion problems, dark/light mode issues, and reduced-motion behavior.

Best implementation
Use browser emulation and Playwright context options for touch/user preferences, then physically use the interface on a touch device. Every important action should remain keyboard accessible.

WHEN EMULATION IS NOT ENOUGH

Real-device strategy

Use real hardware whenever the bug could depend on the operating system, browser chrome, touch, virtual keyboard, device performance, memory, or hardware integration.

Xcode Simulator — free Apple coverage

Free with Xcode on macOS and far more realistic for iOS/iPadOS Safari behavior than simply shrinking a desktop browser window.

Install Xcode from the Mac App Store, finish first-launch setup, then add simulator runtimes in Xcode → Settings → Components. Safari's Develop menu can open pages in installed simulators. Use several OS/runtime versions when compatibility matters.

Physical iPhone/iPad + Safari Web Inspector

Use a real Apple device for the highest-confidence Safari/touch/keyboard/performance check you can do locally.

Enable Safari developer features on the Mac, connect/pair the iPhone or iPad, enable inspection on the device as required, then inspect the device's Safari page from the Mac Develop menu. This is the right escalation step for bugs that only appear on actual hardware.

Physical devices on the same Wi-Fi

BrowserSync gives a local development URL that other phones/tablets/computers can open, with synchronized reloads and optional mirrored interactions.

Start BrowserSync in server or proxy mode. Copy the printed External URL into each device. Keep devices on the same trusted network. Disable Ghost Mode when mirrored clicks/scroll/forms would interfere with independent testing.

Real-device cloud — BrowserStack or equivalent

Use a cloud service when you need device/OS combinations you do not own, remote team access, screenshots/video, or repeatable release checks across real hardware.

BrowserStack is commercial rather than open source, but it supports manual and automated testing on remote browsers/devices and can reach localhost/staging through BrowserStack Local. Comparable paid services include Sauce Labs and LambdaTest. Use cloud hardware strategically rather than replacing fast local checks with expensive remote sessions.

MINIMUM COVERAGE

Practical release matrix

Adapt the matrix to your analytics and audience. The goal is representative coverage, not testing every device ever made.

Browser engines

Chromium + Firefox + WebKit/Safari. Add branded Edge/Chrome only when enterprise policies or browser-specific behavior matter.

Responsive widths

Check narrow phone, common phone, tablet, laptop, and wide desktop ranges. Resize continuously too—bugs often appear between named device presets.

Critical UI states

Menus, forms, validation, modals, authentication, empty/loading/error states, keyboard focus, long text, zoom, and content overflow.

User preferences

Light/dark mode, reduced motion, increased text/zoom, keyboard-only use, and touch where applicable.

Slow conditions

Throttle network/CPU, reload uncached, inspect large assets, and make sure loading/error states remain usable.

Real hardware

At least one current iPhone/iPad Safari pass and one Android/Chrome pass for important public releases, using owned devices or a real-device cloud.
