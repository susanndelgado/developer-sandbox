ROSETTA STONE

Modern Agenda

Rosetta Stone · Multi-Technology Application
One conference agenda application rebuilt across modern technologies.

PROJECT FOUNDATION

Purpose & Goal

The reason this Rosetta Stone exists and what stays constant while the implementation technology changes.
  • Modernize an agenda application based on the conference agenda system you previously built.
  • Keep the same general application problem, data, functionality and visual target.
  • Rebuild it with current languages and frameworks so the differences between technologies are visible.
  • Compare syntax, structure, typing, rendering, state, requests, architecture and tooling.
LEGACY REFERENCE

Original / Legacy Baseline

The application problem and corporate-style conference structure the modern implementations are comparing against.
Original conference-style agenda
The baseline is the real conference-program problem rather than a tutorial task list.
Structured corporate-style data
The shared data resembles the nested agenda output used by corporate conference systems.
Days → sessions → sections / presentations
The hierarchy preserves scheduled sessions with nested presentation-level content.
Speakers / moderators
Faculty-style people data remains part of the application model.
Locations / venues
Sessions retain location and venue information used for display and filtering.
Session types / categories
Sessions can be grouped and filtered by program type and category.
Accreditation
The model preserves accreditation as conference-program metadata.
Legacy implementation
Historical baseline: JavaScript, PHP, cURL, jQuery and related legacy frontend/server techniques.
SHARED RULES

Shared Project Contract

These rules keep the Rosetta comparison meaningful across every implementation.
Same fictional corporate conference data
Every phase starts from the same canonical agenda dataset.
Same major agenda behaviors
Search, filtering, nested sessions, presentations and interaction remain recognizable.
Same visual design
The visible design target stays consistent so implementation differences are easier to compare.
Same expected output
Each phase is judged against the same user-facing result.
Technology changes; project problem does not
Architecture and syntax may change; the application requirement stays stable.
